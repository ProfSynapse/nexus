## Summary

Borrow five bounded ideas from `pingdotgg/t3code` and adapt them to Nexus's existing architecture:

1. A typed runtime-event protocol and pure chat-turn reducer.
2. A small promise-based `DrainableWorker` primitive.
3. A provider driver/instance boundary behind the current adapter registry.
4. A complete tool-policy inventory with conservative parallel-safety enforcement.
5. Durable operation receipts for mutating tool calls.

The work shipped as six independently verifiable pull-request-sized phases. This is not a proposal to port t3code's Effect runtime, server stack, monorepo shape, full event vocabulary, Git checkpoint mechanism, permission-mode UI, or per-turn undo system. Nexus borrows the contracts and failure-handling ideas while retaining its Obsidian-native, mobile-compatible, JSONL-first architecture.

The dependency shape is:

```text
DrainableWorker ─────────────────────────────────────────────── independent

Typed provider events → ChatTurnReducer → Provider driver SPI

Tool execution policy ─┬→ parallel-safety enforcement
                       └→ durable operation receipts
```

The typed event/reducer boundary, `DrainableWorker`, provider SPI, policy inventory, parallel enforcement, and durable receipts are implemented. A permission/diff/undo mockup was reviewed on 2026-08-21 and rejected as disproportionate to the remaining risk: Nexus already confines registered vault operations, uses reversible archive behavior, and exposes tool activity in the existing toolbar. No production permission or undo UI will be built from this plan.

### Post-implementation audit hardening

An independent whole-tree review after PR 6 found eight reliability/privacy gaps. They were repaired on 2026-08-21 without reviving the rejected permission or undo UI:

- Provider-local tool IDs are scoped by assistant turn and continuation response, so synthesized IDs cannot collide across turns or recursive tool rounds.
- Read-only tool results bypass durable receipts; note bodies and other read data are not copied into workspace JSONL.
- A window-scoped in-flight coordinator covers same-realm plugin reload overlap, while SQLite `INSERT OR IGNORE` claim results arbitrate separate repository owners that share a cache.
- Failed and aborted runtime terminals persist `invalid`/`aborted` message state, and chat/workflow callers receive failure instead of false success.
- Receipt recovery keeps a modtime-backed per-workspace event index instead of rescanning the full JSONL stream for every new operation.
- Conversation embedding work drains before the embedding engine is disposed.
- Service/provider cleanup is awaited; disposal of an old WebLLM instance cannot clear its replacement.
- Truncated receipt payloads are bounded by actual UTF-8 bytes, including multibyte and escaped content.

Automated evidence after these repairs: 381 suites passed (5 skipped), 4,699 tests passed (36 skipped), focused regression lanes passed, typecheck and lint passed, the 404-module mobile reachability gate passed, schema/catalog/documented-command checks passed, and the production build passed. The independent post-fix review approved the final tree after two revision loops.

## What the Code Does Today

### Streaming and Chat State

- `src/services/llm/adapters/types.ts` defines `StreamChunk` as a bag of optional fields around `content` and `complete`.
- `reasoning`, `reasoningComplete`, `toolCalls`, `toolCallsReady`, usage, metadata, and completion can occur in ambiguous combinations.
- Similar chunk shapes are redeclared in `StreamingResponseService`, `ChatService`, `ConversationManager`, `ToolContinuationService`, `SubagentExecutor`, and UI controllers.
- `MessageStreamHandler` infers whether a `complete` chunk is truly terminal by checking whether tool calls contain execution results.
- `MessageStreamHandler` also contains a post-loop safety net that forces the message to `complete`, evidence that terminal state is not represented consistently upstream.
- `StreamingOrchestrator` and `ToolContinuationService` remap chunks again while coordinating tool ping-pong.
- `SSEStreamProcessor` already provides useful shared accumulation and in-band error behavior; the new protocol should sit above it before adapters are migrated directly.
- Mobile provider streams may arrive as one buffered chunk, so no reducer rule may depend on desktop timing or intermediate frames.

### Existing Canonical Message Work

`docs/plans/canonical-message-pipeline-plan.md` and `tests/unit/CanonicalMessagePipeline.phase3.test.ts` cover messages traveling into providers and tool continuations. That work removed an input-side remap and must remain intact.

This plan addresses the opposite direction:

```text
provider response frames
        ↓
canonical runtime events
        ↓
pure turn state
        ↓
UI + persistence + tool continuation
```

It complements the canonical input-message pipeline; it does not reopen it.

### Background Work

- `IndexingQueue` owns a bespoke queue/process loop with pause polling and timing-based yields.
- `ConversationEmbeddingWatcher` tests wait with short sleeps for background work to finish.
- `MessageQueueService` has queue behavior but no shared deterministic `drain()` contract.
- Several tests therefore prove eventual timing rather than explicit completion.

### Provider Lifecycle

- `AdapterRegistry` stores one adapter per provider string.
- Provider initialization is a long sequence of provider-specific branches and dynamic imports.
- Alias fallback conflates provider identity with credential/runtime instance selection.
- WebLLM cleanup has a registry-specific special case rather than a common lifecycle contract.
- Dynamic imports correctly protect the mobile startup graph and must remain behind compatibility checks.

### Tool Execution

- `ITool` describes identity, schemas, execution, and optional status labels, but not side effects, replay behavior, parallel safety, or undo capability.
- `ToolBatchExecutionService` honors a caller's `parallel` strategy with `Promise.all()` without checking whether selected tools can safely overlap.
- `DirectToolExecutor` already passes provider tool-call IDs into ToolManager batch execution and is the natural native-chat origin/operation boundary.
- Native chat executes directly on desktop and mobile; external clients reach the same agents through MCP.
- Tool trace events are observability records and are not authoritative receipts.

### Persistence

- Workspace, conversation, and task JSONL streams are authoritative; SQLite is rebuildable.
- `ReconcilePipeline` deduplicates event application, not command side effects.
- A mutation written only to SQLite disappears on `Nexus: Rebuild cache`.
- New durable data therefore needs a JSONL event, an applier case, a SQLite projection where queried, startup readiness guards, and a real rebuild test.
- `SnapshotArchiveService` proves DataAdapter-based snapshot mechanics are possible on mobile, but its co-located `_archive` layout is not suitable for per-turn chat history.

## Architecture Phase

### 1. Typed Runtime Events and Pure Turn Reducer

#### Event Contract

Create a small canonical union rather than reproducing t3code's full vocabulary:

```typescript
export type ChatRuntimeEvent =
  | { type: 'assistant.delta'; text: string }
  | {
      type: 'reasoning.delta';
      text: string;
      blockId?: string;
      encryptedContent?: string;
    }
  | { type: 'reasoning.completed'; blockId?: string }
  | { type: 'tool.snapshot'; calls: ToolCall[]; ready: boolean }
  | { type: 'tool.execution.started'; operationId: string; call: ToolCall }
  | {
      type: 'tool.execution.completed';
      operationId: string;
      call: ToolCall;
      success: boolean;
    }
  | { type: 'usage.updated'; usage: TokenUsage; cost?: CostDetails }
  | { type: 'response.metadata'; metadata: Record<string, unknown> }
  | { type: 'turn.completed'; finishReason?: LLMResponse['finishReason'] }
  | { type: 'turn.aborted'; reason?: string }
  | { type: 'turn.failed'; error: LLMProviderErrorInfo };
```

`tool.snapshot` is deliberately compatible with the current shared tool-call accumulator. Adapters that expose argument deltas may still accumulate them in the shared stream processor. Nexus does not need a lower-level event for every provider frame.

#### Reducer Contract

```typescript
export type ChatTurnPhase =
  | 'pending'
  | 'streaming'
  | 'waiting-for-tool'
  | 'executing-tool'
  | 'complete'
  | 'aborted'
  | 'failed';

export interface ChatTurnState {
  phase: ChatTurnPhase;
  content: string;
  reasoning: ReasoningState;
  toolCalls: ToolCall[];
  usage?: TokenUsage;
  cost?: CostDetails;
  metadata: Record<string, unknown>;
  terminalEvent?: Extract<
    ChatRuntimeEvent,
    { type: 'turn.completed' | 'turn.aborted' | 'turn.failed' }
  >;
}

export function reduceChatTurn(
  state: ChatTurnState,
  event: ChatRuntimeEvent
): ChatTurnState;
```

Required invariants:

1. Exactly one terminal event settles a turn.
2. Repeated identical terminal events are idempotent; a conflicting terminal event is a programmer error surfaced in development/tests.
3. No non-terminal event mutates an already terminal state.
4. Tool snapshots merge deterministically by stable tool-call ID, then provider index as a fallback.
5. `ready: false` never triggers execution.
6. Tool execution results are display/state events and are never executed again by branches or subagents.
7. Usage and metadata merge with explicit rules; no truthy/falsy shortcuts drop zero values.
8. Abort preserves partial content and reasoning.
9. Failure never becomes a successful empty bubble.
10. Desktop incremental streams and mobile buffered streams reduce to equivalent terminal state.

#### Migration Boundary

PR 2 added one temporary compatibility component:

```typescript
export function normalizeLegacyStreamChunk(chunk: StreamChunk): ChatRuntimeEvent[];
```

PR 3 deleted it after completing this migration order:

1. Introduce events, reducer, and characterization tests without changing adapter output.
2. Normalize provider `StreamChunk` values once at the orchestrator boundary.
3. Make `StreamingResponseService` and `MessageStreamHandler` consume reduced state/events.
4. Route shared SSE, buffered mobile, Responses API, CLI, Ollama, and WebLLM output through that common mapper.
5. Keep `StreamChunk` as a provider-response DTO below the runtime boundary, because response completion is not turn completion.
6. Delete duplicate chat-layer chunk interfaces and `complete` inference after every production consumer passes the contract lane.

The temporary UI normalizer is gone. `ProviderStreamEventMapper` is the stable
provider-response boundary, not a second chat protocol: only
`StreamingOrchestrator` and `ToolContinuationService` consume the provider DTO.

#### Persistence Boundary

Runtime events are in-memory coordination, not a second event store. Preserve the current message persistence cadence:

- Update in-memory/UI state incrementally.
- Persist bounded draft/checkpoint state at existing safe points.
- Persist the final `ChatMessage` and tool results through the existing conversation repository.
- Do not append one JSONL record per token.

### 2. DrainableWorker

#### Contract

Create a framework-free primitive:

```typescript
export interface DrainableWorker<T> {
  enqueue(item: T): void;
  drain(): Promise<void>;
  pause(): void;
  resume(): void;
  close(options?: { cancelPending?: boolean }): Promise<void>;
  readonly state: 'running' | 'paused' | 'closing' | 'closed';
}

export interface DrainableWorkerOptions<T> {
  concurrency?: number;
  onError?: (error: unknown, item: T) => void;
}
```

Semantics:

- `drain()` resolves only when the queue is empty and every active item has settled.
- Items enqueued before a pending drain are included; items enqueued after the worker reaches zero begin a new drain epoch.
- Outstanding work increments before scheduling and decrements in `finally`.
- Worker errors are reported through `onError`; they cannot strand `drain()` forever.
- `pause()` stops new starts but does not cancel active work.
- `close()` rejects future enqueues and drains active work unless explicit cancellation is requested.
- Concurrency defaults to one.

#### First Adopters

1. `ConversationEmbeddingWatcher`, replacing sleep-based test synchronization with `drain()`.
2. `IndexingQueue` only if characterization shows its UI-yield, pause, cancel, and progress semantics fit the generic worker without being weakened.
3. `MessageQueueService`, where callers need an explicit flush before teardown or navigation, only if its priority and generation-gating semantics remain intact.

Do not replace UI debounce timers, rendering frame scheduling, stream throttling, or other timing behavior that is not a queue lifecycle.

### 3. Provider Driver and Instance SPI

#### Goal

Separate the kind of provider integration from the configured runtime/credential instance without redesigning provider settings in the same shipment.

```typescript
export type ProviderDriverKind = string & { readonly __brand: 'ProviderDriverKind' };
export type ProviderInstanceId = string & { readonly __brand: 'ProviderInstanceId' };

export interface ProviderDriver<TConfig> {
  readonly kind: ProviderDriverKind;
  readonly displayName: string;
  readonly compatibility: 'all' | 'desktop-only';
  validateConfig(value: unknown): TConfig;
  createInstance(input: {
    instanceId: ProviderInstanceId;
    displayName: string;
    config: TConfig;
    vault?: Vault;
    onSettingsDirty?: () => void;
  }): Promise<ProviderInstance>;
}

export interface ProviderInstance {
  readonly id: ProviderInstanceId;
  readonly driverKind: ProviderDriverKind;
  readonly displayName: string;
  readonly adapter: BaseAdapter;
  dispose(): Promise<void>;
}
```

Design rules:

- Registry lookup is by `ProviderInstanceId`; driver lookup is by `ProviderDriverKind`.
- Existing provider IDs become implicit default instance IDs during migration, so saved conversations and defaults keep resolving.
- Aliases remain a compatibility resolver, not a substitute for instance identity.
- Every instance owns cleanup through `dispose()`; remove WebLLM-specific cleanup from the generic registry.
- Config validation uses existing TypeScript/decoder patterns; add no schema/runtime dependency merely for this SPI.
- A driver module is dynamically imported only after platform compatibility is known.
- `BaseAdapter` continues to own generation. This phase does not rewrite provider HTTP behavior.
- The first shipment creates one instance for each currently configured provider. Multi-account creation/editing is a separate future UI plan.

The typed runtime-event boundary lands first so new drivers implement one output contract instead of inheriting the legacy chunk bag.

### 4. Tool Execution Policy

#### Contract

Extend the tool contract with one internal, machine-readable policy:

```typescript
export type ToolEffect =
  | 'read'
  | 'vault-write'
  | 'external-write'
  | 'destructive'
  | 'unknown';

export type ToolReplayPolicy = 'safe' | 'deduplicate' | 'unsafe';
export type ToolUndoPolicy = 'none' | 'vault-preimage';

export interface ToolExecutionPolicy {
  effect: ToolEffect;
  parallelSafe: boolean;
  replay: ToolReplayPolicy;
  undo: ToolUndoPolicy;
}

export interface ITool<T = unknown, R = unknown> {
  // Existing members remain.
  getExecutionPolicy(): ToolExecutionPolicy;
  getMutationIntent?(params: T): Promise<ToolMutationIntent>;
}
```

`BaseTool` supplies the conservative default:

```typescript
{
  effect: 'unknown',
  parallelSafe: false,
  replay: 'unsafe',
  undo: 'none'
}
```

#### Inventory Gate

Before enforcement:

1. Generate the live tool catalog.
2. Inventory every registered tool from source, not documentation.
3. Add an explicit policy to every concrete tool.
4. Add a contract test that fails when any registered tool still inherits `unknown` outside an allowlist with an owner and expiry.
5. Review path-taking tools against `src/core/vaultPath.ts` and `VaultOperations`.
6. Regenerate `cli-first-tool-schemas.json` only if policy metadata becomes caller-visible.

Do not turn on permission or parallel enforcement while most tools still inherit the conservative default; doing so would silently change broad product behavior before the inventory is trustworthy.

#### Parallel Enforcement

- `parallel` is accepted only when every selected tool declares `parallelSafe: true`.
- A mixed or unsafe batch returns an actionable error naming the incompatible command(s) and asks the caller to retry serially.
- Nexus does not silently downgrade parallel to serial because that hides a caller contract violation.
- Serial execution remains the default.

### 5. Durable Operation Receipts

#### Purpose

Prevent a retried tool request from silently applying the same mutation twice when Nexus can identify the retry. This is duplicate suppression, not universal exactly-once execution.

#### Operation Identity

```typescript
export type ToolExecutionOrigin =
  | 'native-chat'
  | 'subagent'
  | 'workflow'
  | 'external-mcp';

export interface ToolOperationIdentity {
  operationId: string;
  signature: string;
  origin: ToolExecutionOrigin;
  workspaceId: string;
  sessionId: string;
  conversationId?: string;
  messageId?: string;
  turnId?: string;
}
```

Rules:

- Native chat derives the base operation ID from the provider tool-call ID and the ToolManager call index.
- Subagents retain the original executed tool IDs for display and must not redispatch accumulated tool calls.
- Workflows derive a stable ID from workflow run ID plus step ID.
- External MCP accepts an optional top-level `operationId`; absent one, Nexus records a generated non-replayable receipt but cannot suppress a client retry reliably.
- The signature hashes workspace, agent, tool, and canonicalized tool parameters. Volatile conversation context is excluded.
- The same operation ID with a different signature fails as a conflict.
- Persist only the signature, safe command summary, bounded result summary, and sanitized error data. Never persist secrets or full credential-bearing arguments.

#### Receipt States

```typescript
export type ToolOperationStatus =
  | 'started'
  | 'completed'
  | 'failed'
  | 'indeterminate';
```

Execution behavior:

1. Read any existing receipt after storage is query-ready.
2. If `completed` with the same signature, return the recorded bounded result without executing.
3. If the ID exists with a different signature, reject it.
4. Append `tool_operation_started` before dispatch.
5. Execute once.
6. Append `tool_operation_completed` or `tool_operation_failed` after dispatch settles.
7. If Nexus restarts after `started` but before a terminal receipt:
   - `replay: safe` may retry automatically.
   - `replay: deduplicate` invokes the tool-specific reconciliation path.
   - `replay: unsafe` becomes `indeterminate` and refuses automatic replay.

This contract is honest about the unavoidable crash window between an external side effect and the terminal receipt write.

#### Persistence Shape

Use the existing workspace stream rather than adding a fourth event category:

```typescript
type ToolOperationEvent =
  | ToolOperationStartedEvent
  | ToolOperationCompletedEvent
  | ToolOperationFailedEvent
  | ToolOperationMarkedIndeterminateEvent;
```

Required storage work:

- Add the event variants to `WorkspaceEvent` and `isWorkspaceEvent`.
- Append through a dedicated `ToolOperationRepository` in JSONL-first order.
- Add a `tool_operation_receipts` SQLite table and indexes for `operationId`, `workspaceId`, and status.
- Add every event case to `WorkspaceEventApplier`.
- Update fresh schema, migrations, adapter interfaces, and test fakes together.
- Await `waitForQueryReady()` before duplicate lookup.
- Prove receipts survive `Nexus: Rebuild cache` in a real vault.

Trace data remains best-effort observability and does not decide whether a tool executes.

### Rejected Follow-on: Native-Chat Permission Modes

> **Not active scope.** This design was explored but rejected during product
> review on 2026-08-21. It remains here only as decision history and must not be

#### Modes

```typescript
export type ToolPermissionMode =
  | 'supervised'
  | 'allow-vault-edits'
  | 'full-access';
```

| Mode | Read | Reversible vault write | External write | Destructive / unknown |
|------|------|------------------------|----------------|-----------------------|
| `supervised` | Allow | Ask | Ask | Ask |
| `allow-vault-edits` | Allow | Allow when declared and preimage-capable | Ask | Ask |
| `full-access` | Allow | Allow | Allow | Allow, subject to hard Nexus guards |

Hard guards do not disappear in full access:

- AI-facing destructive delete remains unavailable; archive stays the tool contract.
- Vault paths remain confined through `src/core/vaultPath.ts`.
- Tools remain limited to registered schemas and app capability gates.
- Parallel safety and operation receipt rules still apply.
- Provider/platform availability still applies.

#### Origin Behavior

- Native parent chat uses the selected conversation mode.
- Subagents inherit the parent conversation mode and report approval requests through the parent surface.
- Workflows are non-interactive. A step that requires approval returns a recoverable failure naming the mode/policy needed; it never hangs.
- External MCP has `approvalAuthority: delegated`. Nexus does not open an Obsidian modal for a remote host request. Existing external behavior is preserved while hard Nexus guards, policy metadata, and receipts still apply.

#### Approval Lifecycle

- Approval is scoped to one operation ID, signature, and tool policy.
- Editing parameters invalidates the approval.
- Deny returns a structured tool result the model can recover from.
- Abort, plugin unload, conversation switch, or stale operation cancels the pending approval and settles its promise.
- Pending approvals are not restored after restart in v1; they become cancelled, never silently allowed.
- The mode is stored in conversation metadata with a settings-level default. Existing conversations default to `supervised` only when enforcement is deliberately enabled after inventory and UX acceptance.

#### Supported Mutation Intent

Tools with `undo: 'vault-preimage'` return a parameter-aware intent before execution:

```typescript
export type ToolMutationIntent =

  | { kind: 'modify'; path: VaultPath }
  | { kind: 'move'; from: VaultPath; to: VaultPath }
  | { kind: 'archive'; from: VaultPath; to: VaultPath }
  | { kind: 'copy'; from: VaultPath; to: VaultPath }
  | { kind: 'multi'; operations: ToolMutationIntent[] };
```

Every untrusted string is resolved through `src/core/vaultPath.ts` before it reaches this contract. Mutations execute through `VaultOperations`, not direct `vault.*`, `adapter.*`, Node filesystem APIs, or Git.

#### Capture Protocol

For each native-chat turn:

1. Resolve and validate the declared mutation intent.
2. Capture the pre-state, existence, and content hash for supported targets.
3. Execute through the normal tool path and operation receipt boundary.
4. Capture the post-state and content hash after success.
5. Compute a bounded summary and diff off the render path.
6. Append one `turn_change_set_recorded` conversation event referencing the preimage artifacts.
7. Project a queryable change-set summary into SQLite.
8. Render the summary under the associated assistant/tool turn.

Initial supported tools should include the core text and canvas mutation paths:

- `content write`, `content replace`, `content insert`, `content set-property`
- `storage move`, `storage copy`, `storage archive`
- `canvas write`, `canvas update`

Task, workspace, prompt, generated-media, app, and external-provider mutations may display a non-undoable operation summary, but are not restored from file preimages in v1.

#### Artifact Storage

- The change-set manifest is durable domain data: conversation JSONL first, SQLite projection second.
- Preimage payloads live under a resolver-derived managed artifact path beneath `VaultRootResolution.dataPath`, never a hardcoded `Nexus` or `.nexus` path.
- Suggested layout:

```text
<dataPath>/change-sets/<conversationId>/<turnId>/<entryId>.json
```

- Extend vault-root relocation/migration so this managed artifact tree moves with the configured data root.
- Use DataAdapter/VaultOperations-compatible APIs on desktop and mobile.
- Record a content hash and byte count in the manifest; a missing or corrupt artifact makes undo unavailable without corrupting conversation history.
- V1 captures UTF-8 text/canvas files only, up to 1 MiB per file and 5 MiB per turn. Larger or binary targets are marked `not-captured` with a user-visible reason.
- Retain the latest 20 captured turns per conversation. Pruning is explicit, event-recorded, and tested against sync conflicts; do not silently delete referenced artifacts.

#### Undo Protocol

Undo is a UI-authorized action and may restore or trash files even though AI tools expose only reversible archive commands.

1. Load and verify every referenced preimage.
2. Preflight the entire change set before mutating anything.
3. Require current target hashes to equal the recorded post-state.
4. Refuse the whole operation on a conflict and name the changed path(s).
5. For modified files, restore the preimage through `VaultOperations.process`/the appropriate facade method.
6. For files created by the turn, move the unchanged file to Obsidian trash.
7. For moves/archives, restore only when the destination is unchanged and the original path is free.
8. For copies, trash only the unchanged copy.
9. Append `turn_change_set_reverted` after success.
10. Treat a repeated revert request as idempotent success.

If a failure occurs after preflight but during a multi-file restore, report a partial failure, retain the change set, and offer a retry only for still-applicable entries. Never overwrite user edits to make an undo succeed.

## Acceptance Criteria

### Product

- A stream can end only through explicit completed, aborted, or failed events.
- Users never receive a successful empty bubble for a provider stream error.
- Tool activity remains inspectable through the existing chat toolbar and history surfaces.
- Routine vault operations do not acquire a second permission or undo workflow.

### Reliability

- Background queue tests use `drain()` instead of timing sleeps.
- Duplicate completed operation IDs do not execute twice.
- Crash-window operations are reported honestly as safe-to-retry, reconciled, or indeterminate according to policy.
- Unsafe tools cannot be executed in parallel.
- Receipts survive cache rebuild and suppress exact duplicate mutations.
- Mobile buffered and desktop streaming paths produce equivalent final turn state.
- Provider instance cleanup is uniform and does not require registry-specific branches.

### Engineering

- No Effect, Git, queue, provider SDK, or diff runtime dependency is added.
- The existing canonical input-message pipeline regression lane remains green.
- Every live registered tool has explicit execution policy metadata before enforcement.
- JSONL remains authoritative and every new event has a replay applier.
- No hardcoded storage root or direct unconfined vault mutation is introduced.
- No desktop-only import enters the mobile startup graph.
- Focused unit/contract lanes, build, mobile reachability, live provider checks, live Obsidian checks, and cache rebuild verification pass.

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| A runtime-event rewrite destabilizes working adapters | Keep characterized wire parsing below one provider-response mapper, make orchestration own turn terminals, and delete the UI legacy seam |
| Event vocabulary grows into a second application framework | Keep the union limited to observable turn state and never persist token events |
| Duplicate receipts imply exactly-once guarantees Nexus cannot provide | Coordinate same-realm owners, use the shared SQLite projection as the local atomic claim, model `started` crash windows explicitly, and block unsafe automatic replay. Unsynchronized devices can still race before vault sync; receipts intentionally do not claim distributed exactly-once execution. |
| Tool metadata is wrong or incomplete | Conservative default, generated inventory, explicit policy on every registered tool, enforcement only after the gate passes |
| Provider SPI expands into a settings redesign | Keep one implicit default instance per driver and defer multi-instance UI |
| Mobile plugin load regresses through a driver/storage import | Dynamic imports after compatibility checks plus the reachability gate and real-device smoke |
| Existing unrelated worktree edits are overwritten | Implement each PR from a clean worktree or preserve/rebase around user-owned changes |
