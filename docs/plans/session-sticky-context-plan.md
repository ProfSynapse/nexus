## Summary

Today every tool call — from the CLI, from an MCP client, or from the model inside
native chat — must restate `workspaceId` and `sessionId`, and every CLI command
must restate `--vault` when more than one vault is open. The caller is an AI agent
that cannot see the shell, so the repetition costs tokens on every turn and, when
the agent mimics the `"workspaceId":"default"` example, silently files a whole
session's traces under the wrong workspace (#214).

The fix is a **contract change on the server**, not state in any client:

1. **The vault remembers.** A session's workspace is bound once (an explicit
   `workspaceId` on a successful `useTools` call, or a successful
   `memory load-workspace`) and every later call in that session inherits it.
   The vault also remembers the CLI's *current session*, so a CLI command with no
   `--session` continues where the CLI left off. This bookkeeping is persisted in
   the plugin's data folder inside the vault so it survives a plugin reload.
2. **Nothing defaults silently.** A session that has never been bound still
   fails with the #214 steer. "Pass it once" replaces "pass it every time";
   it never becomes "we guessed."
3. **The CLI finds its vault by where it runs.** Each running plugin publishes
   its vault's folder beside its socket. A CLI invoked from inside a vault folder
   targets that vault with no flag. Outside any vault it falls back to the current
   chain (`--vault` → `NEXUS_VAULT` → single open vault → error listing vaults),
   and `--vault` passed once is remembered through the session.

The MCP and native-chat paths are already routed to one vault, so only (1) and
(2) apply to them. All three paths share the same resolution code.

Rejected alternatives, for the record:

- **State in the CLI** (a `~/.local/share/nexus/cli-context.json`). Prototyped
  and reverted 2026-09-12: it only helps the CLI, and it puts a second source of
  truth outside the vault. Workspace and session state belong with the sessions
  they describe.
- **Follow the focused Obsidian window.** Stateless, but the agent's target would
  silently change when the user clicks a different vault window mid-task.

## Architecture

Everything below was checked against the source on 2026-09-12; file paths are
the ones that change. See *Files reviewed* at the end for what each was
verified to do.

### The one pipeline every MCP and CLI call goes through

```text
IPCTransportManager            one MCPSDKServer per socket connection (serverFactory)
  └ RequestHandlerFactory      setRequestHandler(CallToolRequestSchema) → handleToolCall
      └ RequestRouter.handleRequest('tools/call')
          └ ToolExecutionStrategy.handle
              ├ buildRequestContext → processSession   ← session + workspace resolved HERE
              ├ processParameters   (ValidationService: schema `required`)
              ├ executeTool → agent.executeTool → useTools.execute
              │     └ ToolCliNormalizer.normalizeContext → ToolBatchExecutionService.execute
              └ onToolResponse → connector.onToolResponse → ToolCallTraceService.captureToolCall
```

Two other places validate sessions, and they are not the same case:

- **`connector.callTool` (`src/connector.ts` 430–658) is dead code.** No caller in
  `src/` or `tests/` (the only `callTool` match is the embedded CLI bundle);
  `main.ts` keeps the connector private, so it is not a plugin API; its
  companion `getToolRouter()` has no callers either. It carries its own copy of
  session validation, workspace injection, a silent `'default'` fallback and
  trace capture — a second implementation of exactly the contract this plan
  changes. **PR 0 removes it** so PR 1 changes one pipeline, not one and a half.
  `ToolCallRouter` (`src/services/mcp/ToolCallRouter.ts`) shrinks to whatever
  `validateBatchOperations` still needs, or goes with it.
- **`AgentExecutionManager.processSessionContext` is live.**
  `DirectToolExecutor.ts:373` calls `executeAgentToolWithValidation` whenever the
  chat model invokes a tool in the direct `agentName_toolName` form rather than
  through `useTools`. `DirectToolExecutor` always fills `context.workspaceId`
  from the chat's selection first, so the path never sees `UNBOUND` today, but
  it is a **change site to review in PR 1**: its `applyWorkspaceContext`
  fallback must not become a second, divergent resolution order.

Native chat bypasses the MCP pipeline: `ToolCallService` → `DirectToolExecutor`
→ `ToolBatchExecutionService` (for `useTools`) or → `AgentExecutionManager`
(for direct-form calls), with the chat's selected workspace and session id
carried in `DirectToolExecutionContext`.

### Where the state lives

`SessionContextManager` (`src/services/SessionContextManager.ts`) already
holds session → workspace in memory (`sessionContextMap`) and partitions
friendly session handles per workspace in `sessionHandleMap`, keyed
`"<workspaceId>::<handle>"` — `"Research::nexus-cli"` and
`"default::nexus-cli"` are two sessions, by design. Two facts shape the design:

- To answer "which workspace is this handle in" from the handle alone, the
  manager gains a **handle → bound workspace** map. It is distinct from
  `sessionContextMap`, which `ToolCallTraceService.captureToolCall` overwrites
  on *every* call (line 160) — including unbound discovery calls that ran under
  `default`. Only a deliberate bind writes the new map (see *Bind points*).
- Handles are in-memory today. After a reload `validateSessionId` finds no
  handle entry, `createUniqueSessionDisplayName` sees the old name in storage,
  and a returning `nexus-cli` becomes `nexus-cli-2`. Persisting the handle
  entries alongside the bindings fixes that as a side effect.

Persisted shape — one small JSON document, debounced write on change, read once
at service init:

```text
session-bindings.json
{
  handles:         { "<workspaceId>::<handle>": { id, displaySessionId, workspaceId } },
  handleWorkspace: { "<handle>": "<workspaceId>" },   // last deliberate bind
  cliCurrentSession: "<handle>" | null                // this vault's CLI session
}
```

Location: `resolvePluginStorageRoot(app, plugin).dataRoot`
(`src/database/storage/PluginStoragePathResolver.ts`) — the plugin's internal
data folder inside the vault, never a literal path. On load every `handles`
entry is checked against `SessionService.getAllSessions(workspaceId)` (the only
lookup that searches a non-default workspace; `getSession(id)` only searches
`default`) and dropped if the session is gone. Losing the file degrades to
"pass it once again", never to data loss.

### Resolution order

In `ToolExecutionStrategy.processSession`, *before* `validateSessionId`, because
the handle partition needs the workspace:

```text
sessionId:   explicit  →  cliCurrentSession (CLI connections only)  →  today's fallback
workspaceId: explicit  →  handleWorkspace[handle]                   →  UNBOUND
```

- `UNBOUND` + `toolManager_useTools` → the #214 error from
  `normalizeRequiredWorkspaceId`, reworded: *"This session has no workspace
  yet. Pass `workspaceId` once, or load one with `memory load-workspace`; later
  calls in this session inherit it."* `WORKSPACE_ID_REQUIRED_MESSAGE` and the
  comment block above it in `ToolCliNormalizer.ts` (which currently says "there
  is no session stickiness to fall back on") are updated together.
- `UNBOUND` + `toolManager_getTools` → the session is created under `default` so
  discovery can be the first call, **without** a bind.
- `UNBOUND` + `toolManager_useTools` whose batch is made **entirely** of
  `memory load-workspace` / `memory list-workspaces` / `memory create-workspace`
  → same as discovery: runs under `default` without a bind (added in PR 2 —
  without it the steer told callers to run a command it would itself refuse).
  A mixed batch gets the steer, because one `workspaceId` is stamped on the
  whole batch. Today the CLI's
  client-side `'default'` fill *did* effectively bind via the trace write.
- The resolved values are written onto `params` before `useTools` runs, so
  `normalizeContext` and `ToolBatchExecutionService.validateContext` /
  `validateWorkspaceId` stay strict and unchanged.
- Bound value: the **canonical workspace id**, resolved once with
  `WorkspaceService.getWorkspaceByNameOrId` (exact match; `default` passes
  through). `ToolCallTraceService.resolveWorkspaceId` already does exactly this
  for traces, so a bound session's sessions, states and traces land in one
  store. The partition key uses the same canonical value. Callers still pass
  names; `validateWorkspaceId` accepts ids.

Knowing a connection is the CLI: `cli/mcpLineClient.ts` already sends
`clientInfo: { name: 'nexus-cli' }` on `initialize`. Each IPC connection has its
own `MCPSDKServer`, and `RequestHandlerFactory` holds it, so
`handleNormalExecution` attaches `server.getClientVersion()?.name` (present in
`@modelcontextprotocol/sdk` 1.29.0) to the routed request; `IRequestContext`
gains an optional `clientName`. No new CLI-side protocol.

Native chat: `ToolCallService` enriches each call with the chat's
`sessionId`/`workspaceId` only *"if not already present"*, and
`DirectToolExecutor.mergeToolManagerContext` keeps `params.workspaceId ||
context.workspaceId || 'default'`. So a model that mimics
`"workspaceId":"default"` overrides the user's chat selection today. The chat
fix is the prompt and schema change (below) so the model stops emitting the
field; chat then needs no server inheritance because it already carries the
user's selection. **Decision for PR 1:** leave model-over-chat precedence as is
(a model may legitimately load a different workspace mid-chat), and confirm
`WorkspaceIntegrationService.bindSessionToWorkspace` keeps the chat selection in
step when it does.

### Bind points

A bind writes `handleWorkspace[handle]` and, for CLI connections,
`cliCurrentSession`:

1. `useTools` with an **explicit** `workspaceId` whose result has
   `success !== false`. Note `ToolExecutionStrategy.handle` sets its local
   `success = true` for any non-throwing call, so the check reads the *result*;
   a rejected workspace (returned, not thrown) never binds.
2. A successful `memory load-workspace` inside a batch binds to the workspace
   **actually loaded**. `ToolBatchExecutionService.executeCall` merges the
   tool's top-level fields into `result.data` (it strips `workspaceContext`),
   so the name is `result.data.resolution?.resolvedTo?.name ??
   result.data.context?.name`. The batch service reaches the manager the same
   way it already reaches `WorkspaceService`: `getNexusPlugin(this.app)` →
   `plugin.getService('sessionContextManager')`. `ToolCallTraceService.
   extractWorkspaceHandleFromUseTools` already parses `load-workspace` out of a
   `tool` string for traces; the bind reuses that helper rather than a second
   parser.
3. An explicit `--session <name>` on a CLI connection makes that handle the
   vault's `cliCurrentSession` once the call succeeds.

Switching is the same gesture as choosing: pass a different value once.

### The CLI transport and vault discovery

`IPCTransportManager.startTransport` listens on
`ServerConfiguration.getIPCPath()` (`getPrimaryIpcPath(vaultName, isWindows)` →
`/tmp/nexus_mcp_<vault>.sock`, a named pipe on Windows) and records the socket it
created in `handleListeningStarted` (`ownedSocket`) so teardown removes only its
own. The sidecar note is written in the same place and removed in the same
teardown: `<ipcPath minus .sock>.json` = `{ vaultName, basePath }`, with
`basePath` from `app.vault.adapter.getBasePath()` (FileSystemAdapter — desktop
only, like the IPC transport itself). On Windows the note goes under `%TEMP%`
since the pipe namespace holds no files.

`cli/vaultDiscovery.ts` reads the notes next to the sockets it already lists (a
note with no live socket is ignored). `resolveVault()` in `cli/nexus-cli.ts`
gains one step:

```text
--vault  →  $NEXUS_VAULT  →  innermost running vault whose basePath contains cwd
         →  single open vault  →  error listing vaults
```

The CLI stops filling `workspaceId: 'default'` and `sessionId: 'nexus-cli'`
client-side (`tools`, `playbook`, `use` all do this today) and sends only what
the caller gave; the server owns every default.

### Guidance

Every place that teaches the contract changes from "thread it on every call" to
"choose once, it is remembered":

- `useTools.getParameterSchema` and `getTools.getParameterSchema`
  (`required: ['workspaceId','sessionId','memory','goal','tool']` in both):
  `workspaceId` and `sessionId` leave `required`; descriptions say when to pass
  them. Both known-good examples drop `"workspaceId":"default"`. The
  `ValidationService` `required` check on the MCP path follows the schema.
- `SystemPromptBuilder.buildSessionContext` — currently "Context (REQUIRED in
  every useTools call)" with both ids inlined into both payload examples.
- `nexus --help` (`buildUsage` in `cli/nexus-cli.ts`), `skill/SKILL.md`,
  `cli/agents-snippet.md`, all `skill/playbooks/*.md` (the preamble's step 2:
  *"Thread the workspace into every following call"*; every worked example
  repeats `--workspace X --session Y`).
- A new `nexus context` verb shows what this vault currently remembers for the
  CLI (vault, session, workspace) — read-only, answered by the server.
- `docs/generated/` tool catalog via `npm run schemas:tools`, and the
  `shippedGuidanceCommands` test that validates every example.

## Live verification (2026-09-12, `code` vault, after #384/#386/#387/#385 merged to `main` @ `494c1a27`)

Verified:
- PR 3: `/tmp/nexus_mcp_code.json` published on load (`{vaultName, basePath}`, mode 0600), removed on disable, republished on enable; `nexus vaults` shows the folder; `nexus context` from `~/Documents/Code` with four vaults open selects `code` without `--vault`.
- PR 1/2: unbound `use` → steer; `--session live-check --workspace default` binds both; next call without flags inherits; `nexus context` reflects it; survives plugin reload (when storage is warm). `--session fresh -- memory list-workspaces` runs unbound (exemption); mixed batch on `fresh` → steer; `memory load-workspace` binds via bind point 2; `--workspace "Victory Test"` binds the canonical id (`nexus context` shows name + id); a rejected workspace does not rebind; a failed tool (`success:false`) does not bind.

Found — follow-up needed (PR 4):
1. **Debounced save does not fire while Obsidian is in the background.** The 300 ms `window.setTimeout` in `SessionContextManager.scheduleBindingsSave` sat pending for minutes (Electron background-timer throttling; the CLI is used precisely when Obsidian is not focused). In-memory state was right (`nexus context`), the file lagged until the renderer woke. Fix: write-through with in-flight coalescing (dirty flag), no timer; keep `flushBindings()` for cleanup/tests.
2. **Cold-start race drops restored handles.** A call ~3 s after reload sees storage still hydrating: `validateWorkspaceId` listed only `default`, and `verifyRestoredHandle`'s `getAllSessions` miss dropped `default::live-check` and minted a new id. Fix: never drop a restored handle on a miss — keep it and re-create the session record with the same id (best-effort), so continuity wins over a transient empty read.
3. **`generateSessionId` has one-second resolution.** Two sessions created in the same second (`nexus-cli` unbound call, then `--session live-check`) shared `s-20260912194746`; the second `createSession` was a no-op. Pre-existing, made visible by persistence. Fix: monotonic guard in `generateSessionId` (bump when equal to the last issued id).

## Live verification (2026-09-14, `code` vault, after #388 merged to `main` @ `e903fcb4`)

The JSONL store holds exactly one `session_created` for this session (no duplicate from the re-create path).
3. **Same-second ids:** two sessions created concurrently in one second got `s-20260914120251` and `s-20260914120252` — distinct and monotonic.
